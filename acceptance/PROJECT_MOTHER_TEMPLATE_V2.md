# 软件／系统项目不可降级母版 V2.2

> 用途：每个独立 Windows EXE 项目复制一份，作为该项目当前候选版本的验收索引。上位约束是 [HIGH_STANDARD_EXECUTION_POLICY.md](HIGH_STANDARD_EXECUTION_POLICY.md)；本模板只把它变成可执行、可审计的流程，不删减硬门。
>
> 核心区分：**工程验收通过 ≠ 业务内容完成 ≠ 项目获准发布**。任何状态、百分比或文件名都不能代替当前候选版本的证据。

> 冻结目标：**做成一个真实、完整、可验证、可复现、可审计、可长期使用的最终系统。**不到标准，明确写 `FAIL / BLOCKED / PENDING`，绝不报“完成”。

## 使用规则（先读）

1. 立项时冻结原始需求、完整版本范围、验收项、阈值、权重和证据方法；不能为了过门而事后删难项、改权重或把 MVP 改名为“完整版”。变更须留下批准人、理由、影响和新基线 ID。
2. 一个项目保留一张决策卡、一份需求／业务验收清单、一份追加式证据账本、一份发布清单。下方细节可用链接引用，不重复抄写日志。
3. 每次候选版本用新的 `candidate_id`；记录源码 commit/tree、配置、依赖、数据、模型及构建环境。旧版本 PASS 不可复制到新候选。
4. 进度百分比只表示**已按冻结标准且有证据验收的覆盖率**，不是工作量估计。分母未冻结或证据不足时填 `未核证`，不得猜数。任何硬门非 PASS，发布仍为 NO。
5. 开发中允许定向快测以节省时间；候选冻结后必须跑完整链。任何实质代码、配置、模型、数据处理、网络、UI、打包或依赖变更均使旧最终验收失效，并触发本版完整重验；证据过期同样不能沿用旧 PASS。
6. 项目级额外硬门须记录用户批准的依据。**独立 EXE 不自动等于独立 Git 仓库**；不得把工具或 Issue 中自行新增的条件冒充用户冻结标准。
7. 母版是执行索引，不是完成证明。每次实际推进必须产出可核查的代码修复、数据／来源恢复、可复现测试或验收证据；只增加规则、改标题、关闭 Issue、移动仓库不能算功能进展。

### 状态的精确定义

- 单项检查保留原始状态：`PASS / FAIL / PENDING / BLOCKED / WARNING / UNAVAILABLE / SKIPPED / UNKNOWN`。只认与当前候选匹配、有可复核证据、未过期的 `PASS`。
- `FAIL`＝已执行且不满足；`BLOCKED`＝关键依赖或外部条件阻断；`PENDING`＝尚未执行。后三者绝不相互改写为 PASS。
- 汇总 Gate：有明确硬失败为 `FAIL`；无失败但有未完成／无法核证项为 `BLOCKED`；**全部强制项 PASS** 才为 `PASS`。
- `工程 Final Gate PASS` 只说明软件按冻结工程链在该候选版本上通过。`业务 Gate PASS` 才说明完整版本的业务范围、深度和实用价值达标。两者未同时 PASS 时，`项目最终 Gate` 不得 PASS。
- 项目业务的 `100%` 是**原始目的下事先批准的完整版本范围**逐项达标，不是“世界上所有知识都已收录”，也不是事后缩小范围的 MVP。

### 百分比算法（不能取代硬门）

每个验收项先冻结 `criterion_id / 权重 / 必达阈值 / 正例 / 反例 / 证据方法 / 责任人`。权重之和各为 100；**每个强制硬门必须映射至少一项正权重准则**，且一票否决。仅当前候选、有效证据的 PASS 项计入分子：

```text
工程 X = Σ(工程 PASS 项预定权重) / Σ(工程冻结权重) × 100%
业务 Y = Σ(业务 PASS 项预定权重) / Σ(业务冻结权重) × 100%
综合 = min(X, Y)
```

分母、权重、阈值或原始需求追溯未获批准时，百分比为 `未核证`，不是 0% 或主观的“约 85%”。若公式出现 `X=100%` 但仍有工程硬门非 PASS，说明准则映射或计分有错：百分比退回 `未核证`，先修计分与证据，不准宣布工程 100%。业务线同理。

## 4. 研发与验证硬门（不删步骤）

严格按上位政策顺序记录：

```text
原始需求恢复 → 业务目的 → 5 Why → 风险边界 → 成功／失败标准
→ Domain Model → 架构 → 功能清单 → 函数清单 → 接口契约 → 数据源
→ NetClient → Storage → Engine → Validation → Evidence → Service → UI
→ Self-Test → Unit Test → Contract Test → Integration Test → Fault Injection
→ Real Network → Business Validation → Counterexample Validation → Reversal Validation
→ Windows Build → Exact EXE → GUI 实体点击 → Same Hash → 工程 Final Gate
→ 业务 Gate → 项目最终 Gate → 唯一成品
```

`Business Validation` 在工程链中检验计算、输出和失败语义真实执行；业务 Gate 另检验完整版本的知识、资料、案例、深度、质量和使用价值已覆盖全部冻结范围。两者不能混作一项。

| gate_id | 明确退出条件／阈值 | 状态 | 当前候选证据 URI＋hash | 执行环境／UTC | 负责人／复核人 | 失效条件 |
|---|---|---|---|---|---|---|
| G-001 | `填写` | PENDING | `填写` | `填写` | `填写` | `填写` |

测试至少覆盖：正常与异常路径、接口契约、集成、空／错／旧数据、DNS／TLS／超时／429／5xx、存储锁／损坏／中断、更新回滚、源冲突、误报成功、反例与逆转。每个故障验证“检测、记录、传播、UI 真实显示、可恢复”，不是只看测试退出码。

测试夹具和故障模拟可用于单元／契约／故障注入，但必须隔离于生产路径并标明证据类别。故障断言通过不等于网络请求成功；失败响应仍保留 FAIL，不能计入 Real Network 或真实生产数据。最终产品不得把测试夹具当正常数据来源。

模型类项目另冻结：Candidate Pool、独立验证、基线、OOS／walk-forward、bootstrap、ablation、稳定性、多种子／窗口、反例、reality check、多重检验修正、合格模型筛选、Champion／Ensemble。无稳定增益则淘汰或输出诚实的无优势结论，不得调标准保模型。

## 6. 三道决策门与机器报告

实际录入请复制 [project-status-v2.template.json](project-status-v2.template.json)，并用 [project-status-v2.schema.json](project-status-v2.schema.json) 校验结构和部分发布逻辑（状态结构版本 2.1）。`entry_points` 必须与冻结功能清单逐项对账；`no_shell` 不是人工随手填写的 PASS，而由逐入口实现、调用、真实输入／数据、测试和效果 Evidence 核验得出。JSON Schema **不能**证明证据真实、哈希相等、功能清单或分母完整、测试确实执行；这些必须由独立校验器、CI 和人工审查核对冻结基线。模板默认 `BLOCKED / NO / null`，复制后不得在尚未执行时改为 PASS。

机器预检必须另读独立冻结的基线，而非从待验报告自行生成应验清单；必须核对全部入口、准则、证据引用、文件原文 hash、当前候选与证据有效期，并重新计算覆盖率。输入清单完整性仍须与实际产品和原始需求独立复核。预检通过只证明它所检查的契约和完整性，不能取代业务判断、真实执行来源、Windows 实测或最终责任人签核。具体执行顺序见 [执行控制表](EXECUTION_CONTROL.md)。

```text
ENGINEERING_GATE = PASS
  iff 当前候选所有工程硬门（包括逐入口禁止空壳）及证据有效，
      并完成本体 Windows/Exact/GUI/Same Hash 链

BUSINESS_GATE = PASS
  iff 原始目的所需、事先冻结的完整版本业务验收项全部达到阈值，
      且反例、逆转、真实使用价值和安全边界均有有效证据

PROJECT_FINAL_GATE = PASS
  iff 禁止空壳硬门 == PASS 且 ENGINEERING_GATE == PASS 且 BUSINESS_GATE == PASS
      且无未解决强制阻断项，所有结论绑定同一候选

RELEASE = YES
  iff PROJECT_FINAL_GATE == PASS 且实测与交付指纹一致
      且唯一当前指定成品／Manifest／Final Report 已由责任人签核
```

工程 PASS、业务 42% 时：`工程 Gate=PASS；业务 Gate=BLOCKED；项目最终 Gate=BLOCKED；RELEASE=NO`。业务 100% 而 Exact EXE 未过亦同理不得发布。**不要在机器报告中预填所有 Gate 为 PASS**；初始检查项为 PENDING，汇总 Gate 为 BLOCKED，发布为 NO。字段以同目录的 JSON 模板为准，不维护第二份容易漂移的样例。

## 8. 18 项组合的高效执行法（不降标）

固定保留全部 18 条项目记录；缺源码仍为 BLOCKED。总表只显示各项目两轨覆盖率与 Gate、当前 SHA／成品 hash、前三个缺口、下一件可验收交付物及负责人，证据点进项目卡。建议同时深推不超过两条主线：一项收口技术验收，一项恢复原始需求与业务内容；其余项目不消失，也不以造空壳充进度。共用 NetClient／Evidence／Release runner 可统一契约并版本化，但 Domain、Engine、数据源和业务阈值必须分别定义。

日常由 CI 与证据账本自动更新；只有新 PASS／FAIL、版本变更、阻断或停滞时通知。每周复核排序、业务范围、过期证据和最大风险；每次阶段汇报输出：工程 X%、业务 Y%、综合 min、已完成、真实 PASS、未完成、BLOCKED、FAIL、最大风险、下一步、三道 Gate、唯一成品 YES／NO。任何百分比若无法证明，明确写 `未核证`。

实际采用两类工作：**开发轮次**完成一个有退出条件的改动并测试；**每小时监督**只核实 GitHub 的变化、失败与证据，不修改代码或代替开发轮次。持续监督不能被描述成持续开发。当前 18 项的目录、范围和下一件产物集中放在执行控制表，不复制成 18 套相互漂移的口号。
